## D1. 학습에 등장하는 한글 음절이 2,350자뿐이다

**현상.** `rand` 토큰의 음절 풀을 **83개 학습 폰트 charset 의 교집합**으로 잡는다
(`korean/split.py:131-138`).

```python
cs = json.load(open(ASSETS / "fonts_korean_v2/train/fonts_charsets.json"))
inter = None
for s in cs.values():
    f = {ord(c) for c in s}
    inter = f if inter is None else inter & f    # 교집합 2,441
cps = inter                                      # _covered() 검사도 교집합 (D8 수정 후)
syls = sorted(chr(c) for c in inter if 0xAC00 <= c <= 0xD7A3)   # → 2,350
```

교집합이 정확히 2,350 인 이유는 **가장 빈약한 폰트가 상한을 정하기 때문**이다. 한글 폰트는
KS X 1001 2,350자 판과 완성형 11,172자 판으로 갈리는데, 83종 중 `GabiaBombaram`·`Gugi`·
`HSSummer`·`HSYuji` 가 2,350자 판이다. 반면 **합집합은 11,172자 전부**다.

ko 풀이 커버하는 음절도 rand 풀의 부분집합이라, 두 경로를 합쳐도 늘지 않는다.

| 경로 | 커버 음절 |
|---|---|
| ko 풀 (`korean_lines.txt` 어절) | 754 (D2 수정 후. 이전엔 chars.txt 합류로 2,345) |
| rand 풀 (폰트 교집합) | 2,350 |
| **합집합 = 모델이 볼 수 있는 전부** | **2,350 / 11,172** |

(ko 경로만으로는 754 음절이고, 나머지 1,596 은 `rand` 로만 등장한다.)

**영향.** 나머지 **8,822 음절은 학습 데이터에 단 한 번도 등장하지 않는다.** 폰트는 그릴 수
있는데도 샘플링 단계에서 배제된 것이다. [`JONGSEONG_STROKE_LOSS.md`](JONGSEONG_STROKE_LOSS.md)
의 "희귀 겹받침이 사실상 학습되지 않았다"는 관찰과 같은 뿌리다.

**개선안.** 교집합 대신 **폰트별 charset 으로 샘플링**한다. `__getitem__` 은 텍스트를 뽑기 전에
이미 `font_id` 를 알고 있으므로(`korean/split.py:80-81`) 구조적으로 가능하고, 필요한 헬퍼
`font_covered_words()` 도 이미 `korean/fontset.py:81` 에 있다 — **오프라인 생성기
(`korean/fontset.py:304-305`)는 실제로 이 방식을 쓰고 온라인 split 경로만 안 쓴다.**
샘플러가 폰트별 풀을 받도록 시그니처를 바꾸면 되고, 폰트 83종 × 풀 캐싱 비용만 든다.
개입 후에는 음절 커버리지와 함께 **한글 CER 전체/단문/장문**을 재서 퇴보가 없는지 확인해야 한다.

재현:
```python
inter = None
for s in json.load(open("assets/fonts_korean_v2/train/fonts_charsets.json")).values():
    f = {ord(c) for c in s}; inter = f if inter is None else inter & f
print(len({c for c in inter if 0xAC00 <= c <= 0xD7A3}))   # 2350
```

## D2. `chars.txt` 가 ko 풀에 낱글자로 섞여 들어간다

**현상.** `build_pools`(`korean/fontset.py:62-64`)가 `chars.txt` 의 음절을 **ko 풀에 1글자
"단어"로 추가**한다. 별도 카테고리가 아니다.

```
ko 풀 7,305 = 5,196 (korean_lines.txt 어절, 이 중 236개가 1글자)
            + 2,109 (chars.txt 신규 낱글자)
→ 최종 1글자 항목 2,345 / 7,305 = 32.1%
```

`rng.choice(ko풀)` 은 균등 추첨이므로 **ko 토큰 3개 중 1개가 의미 없는 낱글자**다.
전체 토큰 기준으로는 `0.45 × 0.321 = 14.4%`. `rand` 15% 와 합치면 **토큰의 약 27%가
무의미 음절 나열**이고, 실제 한글 어절은 28.6% 에 그친다.

**영향.** [`DATA_GENERATION.md`](DATA_GENERATION.md) §8-2 표는 ko 0.45 를 "코퍼스 어절"로만
설명해 이 경로가 드러나지 않는다. 그리고 "학습 텍스트가 부자연스러워 성능이 나쁜가"를 실험할 때
`weights["rand"]` 만 0으로 놓아도 낱글자가 13~14% 계속 들어오므로 **통제가 안 된다.**

### ✅ 수정됨 (2026-08-20)

`build_pools` 에서 chars.txt 합류를 **삭제**했다(옵션으로 남기지도 않았다). `rand` 토큰이 이미
폰트 교집합 2,350 음절을 균등 노출하므로 같은 일을 두 번 하고 있었을 뿐이고, 빼도 **음절
커버리지가 그대로**다.

| | 이전 | 이후 |
|---|---|---|
| ko 풀 | 7,305 | **5,196** (코퍼스 어절만) |
| 그중 1글자 | 2,345 (32.1%) | **236 (4.5%)** — `것`·`게`·`가` 같은 실제 1어절 |
| 전체 토큰 중 무의미 낱글자 | 14.4% | **2.0%** |
| 학습에 등장하는 음절 (ko ∪ rand) | 2,350 | **2,350** (변화 없음) |

`--extra-chars` CLI 인자와 `paths.corpus_chars` config 키도 함께 제거했다.
`chars.txt` 자체는 남아 있고 `korean/alphabet.py`(HTR 알파벳)와 `tools/font_audit.py` 가 계속 쓴다.

> **부수 정정.** 이 경로 때문에 [`JONGSEONG_STROKE_LOSS.md`](JONGSEONG_STROKE_LOSS.md) 의
> "코퍼스 고유 단어 7,305개 중 겹받침 포함 182개(2.5%)" 가 실제보다 부풀려져 있었다.
> 그 182개의 대부분이 `갉`·`갊`·`값`·`걺` 같은 **chars.txt 낱글자**였다. 실제 코퍼스
> **단어** 중 겹받침을 포함하는 것은 **67개(1.3%)** 다 — 겹받침의 실사용 어휘 기반은
> 알려진 것보다 더 좁다.

## D3. `style_text` 의 22.4% 가 단어 중간에서 잘린다

**현상.** `MixedLineSampler.__call__` 마지막 줄이 단어 경계를 보지 않는다.

```python
if len(txt) > self.max_chars:
    txt = txt[: self.max_chars].rstrip()
```

`max_chars` 는 이제 config 에 있다 — `configs/base.yaml` 의 `data.sampler.max_chars`
(기본 style 40 / gen 130). 절단이 단어 경계를 무시하는 문제 자체는 그대로다.

| | 평균 글자수 | 평균 어절수 | `max_chars` 도달(=절단) |
|---|---|---|---|
| style (40자) | 25.3 | 4.51 | **22.4%** |
| gen (130자) | 40.5 | 6.97 | 0.0% |

실제 run 의 sample 1 style 이 `... 확인됐다"고; induct` 로 끝나는데, 정확히 40자이고
`induct` 는 영어 풀에 없는 문자열이다 — 더 긴 단어가 잘린 흔적이다.

**영향.** style 참조 이미지의 끝 글자가 깨진 형태로 렌더된다. 스타일 조건으로만 쓰이므로
치명적이진 않으나, style 텍스트를 드롭하지 않는 Phase 1 에서는 텍스트-이미지 불일치가 아니라
**잘린 글자 자체를 스타일로 학습**하게 된다.

**개선안.** `rsplit(" ", 1)[0]` 로 어절 경계에서 자르거나, `max_chars` 를 CLI 인자로 노출.

## D4. 영어 풀이 사전 덤프에서 균등추첨이라 상용어가 없다

**현상.** `english_words.txt` (dwyl/english-words `words.txt`, 466,551 항목)에서
`^[A-Za-z]{2,12}$` 로 359,671 개를 남기고 **균등 무작위 8,000 개**만 뽑아 고정 어휘로 쓴다
(`korean/fontset.py:68-73`, `n_english=8000`).

원본 사전이 희귀어·고어·학술어 위주라 균등추첨의 결과는:

```
영어 최빈 단어 100개 중 pool 포함: 0개  (the, of, and, to, in … 전부 없음)
pool 표본: subpart, diddlies, restiness, tristigmatic, carduaceous, trophobiosis …
```

원본 upstream `TextSampler` 는 NLTK 실제 코퍼스 6종(103,411 단어)에서 뽑아 상용어가 자연히
포함됐다. 한글판이 소스를 사전 덤프로 바꾸면서 **단어 빈도 정보가 완전히 사라졌다.**

**부수 문제 — seed 의존.** 풀은 `rng.sample` 로 만들어지므로 seed 가 바뀌면 어휘가 통째로 바뀐다.
resume 시 `args.seed + seed_off` 가 들어가므로(`train/core.py`), 예컨대 seed 42 → 15042 로
resume 하면 **영어 어휘 8,000개 중 공통은 186개(2.3%)뿐**이다. 학습 전·후 구간이 사실상 다른
영어 어휘로 돌아간다.

**개선안.** `n_english` 를 키우거나(전체 359,671 을 그대로 써도 메모리는 무시할 수준),
빈도 상위 목록을 섞는다. 한글 샘플러 비중을 건드리는 것보다 싸고 효과가 명확한 개입이다.
resume 시 풀만은 고정 seed 로 만들도록 분리하는 것도 검토.

## D5. held-out 폰트로 데이터를 만들어도 샘플러는 train 폰트 기준이다

**현상**(수정 전). `build_samplers()` 는 `fonts_dir` 인자를 받지 않고 train 폰트 json 을 하드코딩했다.

```python
def make_dataset(..., fonts_dir=None, ...):
    style_s, gen_s = build_samplers(style_range, gen_range, seed=seed)   # ← fonts_dir 안 넘어감
```

따라서 `make_dataset(fonts_dir=".../fonts_korean_v2/test")` 로 held-out 데이터셋을 만들어도
`cps`(_covered 검사)와 `rand` 풀은 **train 폰트 교집합** 그대로다.

**영향.** test 폰트가 그 음절을 못 그리면 렌더 단계에서 **조용히 글자가 삭제**된다
(`render_font.py:74-76`). held-out 평가에서 텍스트가 의도보다 짧아질 수 있다.
실측상 train 폰트끼리도 300라인 중 16라인(5.3%)에서 글자 손실이 있었다.

### ✅ 수정됨 (2026-08-20)

`build_samplers(fonts_dir=...)` 가 **그 폰트 디렉토리의 `fonts_charsets.json`** 을 쓴다
(`charsets_json_for()`; 폰트 경로 **리스트**를 받았거나 json 이 없으면 `paths['korean_fonts_dir']`
로 폴백). `make_dataset` 이 자기 `fonts_dir` 을 그대로 넘기므로 held-out 데이터셋은 자동으로
held-out charset 을 쓴다.

```
train 폰트(83종): cps 2441 (intersection, train)
test  폰트(16종): cps 2499 (intersection, test)   ← 이제 자기 폰트 기준
```

샘플러 로그 끝에 어느 디렉토리의 charset 인지 함께 찍는다.
[D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다) 을 폰트별 샘플링으로 고치면 이 항목도 흡수된다.

## D6. `fonts_charsets.json` 갱신 스크립트가 없다

**현상.** 이 저장소 코드는 이 파일을 **읽기만 한다.** `make_renderers`(`font_square_split.py:107`)
는 로드만 하고, `RenderImage.__init__` 의 `json.dump` 는 주석 처리돼 있다. 폰트와 함께 미리
만들어져 들어온 캐시다.

**영향.** 폰트를 새로 추가하면 그 폰트만 키가 없어 `charset = None` 이 되고,
`Render.render()` 의 글자 필터가 **통째로 꺼진다** → 두부(□)가 학습 데이터에 조용히 섞인다.
에러도 경고도 없다. (현재 83종은 전부 키가 있어 문제없는 상태.)

### ✅ 수정됨 (2026-08-20)

별도 스크립트 대신 **데이터셋을 만들 때 자동 갱신**한다 — `korean/split.py:ensure_font_charsets()`
가 `make_dataset` / `make_english_dataset` 앞에서 호출된다(upstream 은 손대지 않았다).

- json 에 없는 폰트만 cmap 을 읽어 채운다. 최신이면 파일을 건드리지 않는다(멱등)
- 쓰기는 tmp → rename 원자적 교체
- cmap 을 못 읽는 폰트는 조용히 넘기지 않고 경고 — 그 폰트는 charset 필터가 꺼진 채 렌더된다
- 폰트 경로 **리스트**(`split_train_fonts` 결과)를 받으면 그 부모 디렉토리를 대상으로 본다

**깨진 폰트 제외도 함께.** `DEFAULT_EXCLUDE_FONTS`(config `data.exclude_fonts`)에 적힌 폰트는
학습 폰트 목록에서도, charset 교집합 계산에서도 빠진다. 추론의 `--exclude-writers` 와 같은
목록이어야 학습·추론이 어긋나지 않는다.

83폰트 × 2,350음절(교집합) 전수 스캔 결과 이상 글리프는 **하나뿐**이었다:

| 폰트 | 글자 | 글리프 높이 | 그 폰트 중앙값 |
|---|---|---|---|
| `UlsanJunggu.ttf` | `델` | 555px | 74px (**7.5배**) |

이 글자가 한 줄에 들어가면 라인 전체를 64px 로 맞출 때 나머지 글자가 ~8px 로 뭉개진다.

**폰트를 통째로 제외**한다(글자 하나만 charset 에서 빼는 방법도 검토했다). 후자를 쓰면 `델` 이
전 폰트 **교집합**에서 빠져 `rand` 음절 풀이 2,350 → 2,349 로 줄어드는데, 음절 커버리지가 이미
최대 현안이라([D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다)) 음절을 지키는 쪽을 택했다.
제외하면 교집합이 82폰트 기준으로 다시 계산돼 **2,350 이 유지**되고, 학습 writer 는 83 → 82 가 된다.

### ⚠️ 잔여 구멍 — 갱신이 cmap 만 본다 (2026-08-25 실측)

`ensure_font_charsets()` 는 `chr(c) for c in get_cmap(p)` 로 charset 을 만든다. cmap 은
"그릴 수 있다"는 폰트의 *주장*이라, **cmap 엔 있는데 실제로는 안 그려지는 글자**가 그대로 통과한다.
위의 전수 스캔은 `font_audit.py` 의 **기하** 검사였고 빈 글리프는 검사 대상이 아니었다.

실제로 현재 83종에서 발견된다:

| 폰트 | 글자 | 상태 |
|---|---|---|
| `116Watermelon.ttf` | `뢍 멓 묾 쏨 흖` | cmap 에 있으나 **빈 글리프**(`getmask` bbox=None) |

5자 모두 **현재 교집합에 들어 있어** `rand` 가 뽑을 수 있고, 뽑히면 이미지엔 아무것도 안 그려지는데
라벨엔 글자가 남는다 = **이미지-라벨 불일치**. 렌더러의 charset 필터(`render_font.py:75`)는
"cmap 에 없는 글자"만 막지 "cmap 에 있지만 안 그려지는 글자"는 못 막는다.

83종 전체로는 **53종의 charset 이 부풀려져 있고 295,465자**가 실제로는 안 그려진다. 다만
`charset_rule=intersection` 이라 교집합이 이미 가장 빡빡한 폰트에 맞춰져 있어 영향은 위 5자뿐이다
(교집합 2,441 → 2,436자, 한글 2,350 → 2,345). **`union` 모드(영어 폰트)에서는 방어선이 없다.**

**해결:** `tools/font_charset.py` 가 실제로 래스터해서 charset 을 만든다(같은 포맷, 드롭인).
빈 글리프와 placeholder(동일 비트맵을 10자 이상이 공유)를 뺀다. 판정 근거와 ASCII 면제 규칙은
[`docs/FONT_SOURCES.md`](FONT_SOURCES.md) §7 참고.

```bash
.venv/bin/python tools/font_charset.py --fonts-dir assets/fonts_korean_v2/train --force
```

⚠️ 적용하면 교집합에서 위 5자가 빠져 `rand` 음절 풀이 2,350 → 2,345 가 된다. `델` 때와 같은
트레이드오프(음절 커버리지 vs 데이터 정합성)이고, **아직 적용하지 않았다** — 기존 체크포인트의
alphabet 과의 정합성을 먼저 확인해야 한다([D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다)).

## D8. `_covered` 가 합집합으로 검사해 구두점이 렌더에서 조용히 삭제된다

**현상.** 샘플러의 `_covered()` 검사와 `trail`/`wraps`/`specials` 필터는 **83개 폰트 charset 의
합집합**(`cps`, 54,887자)을 쓴다(`korean/split.py:133`, `korean/fontset.py:115-119`).
"어떤 폰트든 하나라도 그릴 수 있으면 통과"이므로, 정작 배정된 폰트가 못 그리는 글자가 그대로 남는다.
그 글자는 렌더 직전에 **경고 없이 삭제**된다(`render_font.py:74-76`).

gen 2,000 라인 측정(`font_id = i % 83`):

```
글자 손실 라인 142 (7.1%), 손실 글자 339
내역: 공백 165 / '…' 128 / '‘' 15 / '’' 15 / '“' 8 / '”' 8
```

`…` 를 못 그리는 폰트가 14종, 곡선 따옴표를 못 그리는 폰트가 3종이다.

**핵심 — 합집합을 쓸 이유가 없다.** 교집합으로 바꿔도 단어 풀은 전혀 줄지 않는다:

| 풀 | 크기 | 교집합으로 전부 커버되는 항목 |
|---|---|---|
| ko | 7,305 | **7,305 (100.0%)** |
| en | 8,000 | **8,000 (100.0%)** |

ko 풀의 한글 음절(2,345)이 이미 교집합(2,350)의 부분집합이고([D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다)),
영어·숫자·기본 ASCII 는 83종이 모두 갖고 있기 때문이다. 합집합과 교집합의 실질 차이는
**`…` `“` `”` `‘` `’` `~` 6글자뿐**이고, 그 6글자가 바로 위에서 삭제되는 글자들이다.

**영향.** 라벨 텍스트는 렌더 결과로 덮어써지므로 이미지-텍스트 불일치는 아니다. 다만
구두점 다양성이 의도보다 낮고(`…` 는 14/83 폰트에서 무효), 손실이 조용히 일어나 측정에 안 잡힌다.

**왜 합집합인가 — 설계가 아니라 잔재다.** git 이력이 분명하다. 최초 커밋 `fe688c8` 에는
`cps`(합집합)만 있었고 `_covered` 는 처음부터 그걸 썼다. 교집합 `inter` 는 `42db287`
("Add 'rand' random-syllable words … intersection of all 61 font charsets -> **tofu-safe**")
에서 **rand 풀을 만들려고 뒤늦게 추가**됐는데, 그 커밋은 `inter` 를 `rand_syllables` 로만 넘기고
`_covered` 에 넘기는 인자는 `cps` 그대로 뒀다. tofu-safe 라는 이유까지 명시해 놓고 `_covered` 는
검토하지 않은 것이다.

합집합을 옹호할 논리가 하나 있기는 하다 — *"폰트 하나가 'Q' 를 빠뜨렸다고 Q 들어간 단어를 전
폰트에서 없앨 수는 없다"*(교집합은 최악 폰트에 어휘가 종속된다). 실제로 그 취약성이
[D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다) 에서 음절 커버리지를 2,350자로 묶은 원인이다.
다만 **현 폰트 구성에서는 그 논리가 공허하다** — 위 표대로 교집합 전환의 풀 손실이 0% 다.

### ✅ 수정됨 (2026-08-20)

`build_samplers`(`korean/split.py`)가 `covered_cps` 로 **교집합**(2,441자)을 넘기도록 바꿨다.
`trail`/`wraps`/`specials` 가 이미 `covered_cps` 로 필터링되는 구조라 자동 반영된다.

측정(gen 2,000 라인, `font_id = i % 83`):

| | 수정 전 | 수정 후 |
|---|---|---|
| 글자 손실 라인 | 142 (7.1%) | **20 (1.0%)** |
| 손실 내역 | 공백 165 / `…` 128 / `‘’“”` 46 | **공백 130 만** |

구두점 삭제는 완전히 사라졌다. 남은 1.0% 는 전부 `JHaebaragi.ttf` 의 공백 문제다 —
`__call__` 의 글자 필터가 `if c == " " or ord(c) in self.cps` 로 **공백을 무조건 통과**시키므로
교집합 전환으로는 해결되지 않는다(아래 부수 발견 참고).

**영어 경로는 union 을 유지했다.** 영어 폰트 177종의 교집합은 **63자**(A-Za-z0-9+공백)뿐이라
구두점이 전멸하고 `gen_number` 의 `%,-.:` 까지 걸려 숫자가 `randint(0,999)` 폴백만 남는다.
`build_english_samplers` docstring 에 사유를 적어 뒀다.

[D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다) 을 폰트별 샘플링으로 고치면 이 항목은 그쪽으로
흡수된다 — 그때 영어 경로도 함께 해결된다(폰트별이면 union/교집합 선택 자체가 없어짐).

**부수 발견 — 공백을 못 그리는 폰트.** `JHaebaragi.ttf` 는 cmap 에 U+0020 이 없다.
이 폰트에 배정되면 렌더 필터가 공백을 전부 지우고 `' '.join(text.split())` 가 한 덩어리로 만들어
**모든 어절이 붙은 한 단어**가 된다(위 표의 "공백 165"가 이것). 83종 중 1종이므로 샘플의 약 1.2%.
이미지와 라벨이 함께 그렇게 되므로 불일치는 아니지만, 띄어쓰기 없는 데이터가 그만큼 섞인다.
폰트를 빼거나, cmap 에 없어도 공백은 보존하도록 예외 처리하면 된다.

## D9. 구두점 비율이 자연 텍스트의 4.6~140배다 (근거 없는 매직 넘버)

**현상.** `_decorate()`(`korean/fontset.py:138-143`)가 토큰마다 두 번 주사위를 굴린다.

```python
if self.wraps and self.rng.random() < self.punct_prob * 0.4:   # 감싸기  → 실효 14%
    a, b = self.rng.choice(self.wraps); tok = f"{a}{tok}{b}"
if self.trail and self.rng.random() < self.punct_prob:          # 후행    → 35%
    tok = tok + self.rng.choice(self.trail)
```

`* 0.4` 는 **최초 커밋부터 있었고 주석도, 별도 인자도 없다.** `punct_prob` 하나로 두 확률을
묶어 조절하려고 상대비를 박아 넣은 매직 넘버다. `punct_prob=0.35`, `special_prob=0.08` 도
`korean/split.py:140-143` 에 하드코딩이라 CLI 노브가 없다.

**같은 코퍼스와 비교하면 과다하다.** `korean_lines.txt` 의 169,014 어절 실측:

| | 샘플러 설정 | 코퍼스 실제 | 배율 |
|---|---|---|---|
| 후행 구두점으로 끝나는 어절 | 35% | **7.6%** | 4.6배 |
| 괄호·따옴표로 감싸인 어절 | 14% | **0.1%** | **140배** |

여기에 독립 특수기호 토큰(`% & @ # * + = / ~ $`)이 8% 더 붙는데, 자연 문장에서 기호가 홀로
어절이 되는 일은 사실상 없다.

**영향.** 글자 모양 학습이 목적이라면 구두점 노출을 늘리는 것 자체는 합리적이다. 문제는
**의도한 값이라는 근거가 없다는 것**이고, [D2](#d2-charstxt-가-ko-풀에-낱글자로-섞여-들어간다)
와 함께 "학습 텍스트가 부자연스러워 성능이 나쁜가" 가설의 교란변수가 된다.

### ✅ 수정됨 (2026-08-20)

`* 0.4` 를 없애고 **`wrap_prob` 를 독립 인자로 분리**했다(`MixedLineSampler.__init__`,
오프라인 생성기는 `--wrap-prob`). 값은 절충안으로 조정 — 코퍼스 실측까지 내리면 괄호·따옴표
12종의 글리프 노출이 7배 줄어 해당 글자 생성 품질이 떨어질 수 있어, 자연 분포와 글리프 커버리지
사이에서 택했다.

| | 수정 전 | 수정 후 | 코퍼스 실측 |
|---|---|---|---|
| 후행 구두점 | 0.35 | **0.20** | 0.076 |
| 감싸기 | 0.14 (= `0.35*0.4`) | **0.05** | 0.001 |
| 특수기호 토큰 | 0.08 | 0.08 (유지) | ~0 |

`_decorate` 5만 회 실측: 감싸기 5.0% / 후행 20.1% — 설정값과 일치.
한글·영어 sampler 양쪽에 동일 적용했고, `samplers:` 로그 줄에 세 값을 찍는다.

재현:
```python
lines = [l for l in open("assets/corpus/korean_lines.txt", encoding="utf-8") if " " in l]
toks  = [w for l in lines for w in l.split()]
print(sum(1 for t in toks if t[-1] in ".,!?…:;") / len(toks))   # 0.076
```

## D10. 한글 코퍼스가 실은 941줄이다 (24배 중복)

총 라인      22,996        고유 라인       941

37~43회로 제각각인 점이 이 해석과 맞는다(텍스트별 이미지 수가 달랐다는 뜻).

**영향.** `build_pools` 가 `set` 으로 접으므로 중복 자체는 무해하다. 문제는 드러나는 사실 쪽이다 —
**한글 어휘 기반이 941줄 / 5,196 어절로 매우 빈약하다.** "1.7MB 코퍼스" 라는 인상과 실제
정보량(고유 텍스트 36KB 수준)의 괴리가 크다. [`JONGSEONG_STROKE_LOSS.md`](JONGSEONG_STROKE_LOSS.md)

[D1](#d1-학습에-등장하는-한글-음절이-2350자뿐이다) 의 음절 커버리지 한계와 결합하면,
한글 텍스트 다양성이 예상보다 훨씬 낮은 상태다.

**개선안.** 코퍼스 자체를 늘리는 게 정공법이다(출처 미확인 문제도 함께 해결 —
